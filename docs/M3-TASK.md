# M3：中继

2026-10-06 确认。

公网中继替守护进程收投递、落盘，守护进程主动外连取回。中继有两种跑法：Cloudflare Worker（默认）和普通 Node 主机，两种跑同一份中继逻辑。做完以后，守护进程离线期间的事件，上线后全部送达且验签通过。

## 依据

- 事件扩展 SEP-3415（`docs/spec/sep-3415-2026-10-06.md`）里和接收端有关的几段：
  - 端点验证，619–628 行
  - 投递约束（必需头、256 KiB、413），651–660 行
  - 确认语义，537 行
  - 未确认的 id 回 503/425，538 行
  - 签名和时间戳，634–641 行
- DESIGN.md 里中继的部分。
- Cloudflare 免费层的事实，2026-10-06 按官方文档核实，原文快照在 `docs/spec/cloudflare-2026-10-06/`：
  - Workers：每天 10 万次请求，每次 10 ms CPU，等待不算 CPU，超额返回错误、不收费。
  - SQLite 版 Durable Object 免费层可用：每天 10 万次请求、1.3 万 GB-s 时长、10 万行写入，单行最大 2 MB。
  - 存储写入要落盘之后响应才会发出去（output gate）。
  - 空闲且可以休眠的 Durable Object 不计时长。

## 设计决定

### 1. 不发布 well-known 文件（和 DESIGN.md 不同）

DESIGN.md 第 47 行要求中继发布 `/.well-known/mcp-webhook-receiver.json` 声明 `/hooks/`。但按 SEP 第 4 种验证方式，这个文件声明的路径前缀之下，任何回调地址都算已验证（624 行）。也就是说，任何人都能用 `https://<中继>/hooks/<随便什么>` 去订阅，服务端不握手就开始投递。这和 DESIGN.md 第 66 行"别人拿不到路径，就没法用你的中继地址去订阅"正好相反。

后果是：别人可以把大量投递引到你的中继上，耗光每天 10 万次的免费请求额度，中继在 UTC 0 点之前都会报错。如果改成在文件里逐条列出已登记的路径，路径就公开了，等于没有随机令牌。

所以只用握手：中继只对守护进程登记过的路径回显 challenge。DESIGN.md 的第 29、47 行跟着改。

### 2. 中继不持有签名密钥，也就不验签

DESIGN 已定。由此有两点：
- 握手包中继验不了签名，只要路径已登记就回显 challenge。路径是守护进程登记的随机令牌，回显就代表你同意在这个路径上收投递，这正是握手要证明的事。
- 事件原样存下，验签、时间戳检查和去重都在守护进程取回之后做。

### 3. 路径有三种状态，和 M1 的接收端一致

| 状态 | 握手包 | 事件 |
| --- | --- | --- |
| 没登记 | 404 | 404 |
| 已登记，待确认 | 回显 challenge | 503（规范的"还没告诉接收方怎么路由"，538 行） |
| 已确认 | 回显 challenge | 落盘后回 200 |

守护进程在 `events/subscribe` 之前登记路径（待确认），拿到订阅 id 后改成已确认，失败就删掉。这和 DESIGN.md 表里"路径已登记但订阅还没确认时收到投递，回 503"那一行对得上。这样中继里存下的投递，订阅一定是确认过的，守护进程取回时不用再暂存未确认订阅的事件。

### 4. 外连通道用短轮询

守护进程每 5 秒用 HTTPS 问一次中继有没有新投递。取到了就处理、确认，取满一批就马上再取，直到取完。

| 方式 | 每天用掉的免费额度（按一天 300 个事件估） | 代价 |
| --- | --- | --- |
| 长轮询（挂起 25 秒） | 时长额度约 85% | 有一点差错就会超额 |
| WebSocket + 休眠 API | 都不到 1% | Node 那边要加 `ws` 运行时依赖或者自己实现协议；两种跑法各写一套传输层；还要处理断线重连 |
| 短轮询，每 5 秒一次（选这个） | 请求额度约 18%，时长额度约 0.2% | 事件平均晚到约 2.5 秒 |

短轮询两种跑法完全相同，不加任何依赖。2.5 秒的延迟和 agent 处理一个事件要花的时间相比可以忽略。

### 5. 时间戳按中继收到的时刻算

中继给每条投递记下收到的时刻。守护进程取回后，拿这个时刻和 `webhook-timestamp` 比较是否在 5 分钟之内（DESIGN 已定，M1 的接收端已经留好了这个参数）。所以守护进程离线多久都不会误拒。

### 6. 认证

- 守护进程和中继之间用一个"中继密钥"认证，走 bearer 头。Worker 存在 secret 里，Node 跑法从环境变量读。守护进程这边只存环境变量名。比较时用常数时间。
- 公网上只开 `POST /hooks/<令牌>` 一个口，其他路径都是 404。

### 7. 存储上限

- 投递一直存到守护进程确认取回才删，不设过期时间。过期删除就等于丢事件。
- 总量上限是 1 万条或 200 MB，满了回 503，让服务端去重试。免费层每个对象可以存 1 GB 到 10 GB（文档两处说法不一），200 MB 留足了余量。

### 8. 超大 body

先看 `Content-Length`，超过 256 KiB 直接回 413，不读 body。没有 `Content-Length` 的读到上限就停，回 413 并断开连接。这条补上 M1 留到 M3 的那个已知限制。缺必需头回 400，规范允许中间设备这样预过滤（655 行）。

### 9. 一份核心，两种跑法

中继的逻辑只用 Web 标准接口写成一个函数：输入 `Request`，输出 `Response`。存储接口是同步的 SQL，因为 `node:sqlite` 和 Durable Object 的 SQLite 都是同步的。

- **Node 跑法：** `evdock relay serve`。用 `node:sqlite`，提供明文 HTTP，TLS 交给前面的反向代理或隧道。DESIGN.md 写的是 `--relay` 开关，这里改成子命令，和现有的命令行风格一致。
- **Worker 跑法：** 一个 Worker 加一个 SQLite 版 Durable Object。Worker 要等 Durable Object 的响应回来才回 2xx，保证落盘在先。

## 交付

### 1. 中继核心：`src/relay/core.ts`

接口：

| 请求 | 谁调 | 行为 |
| --- | --- | --- |
| `POST /hooks/<令牌>` | MCP 服务端 | 见上面的第 3、8 条：落盘后回 200，写失败或存满回 503 |
| `PUT /relay/paths/<令牌>`，body `{"state":"pending"}` 或 `{"state":"confirmed"}` | 守护进程 | 登记或确认路径，回 204 |
| `DELETE /relay/paths/<令牌>` | 守护进程 | 删除路径和它没取走的投递，回 204 |
| `GET /relay/deliveries` | 守护进程 | 最早的一批未确认投递，最多 20 条。每条带序号、令牌、收到时刻、四个必需头，body 用 base64；另有 `more` 表示后面还有 |
| `POST /relay/ack`，body `{"upTo": 序号}` | 守护进程 | 删除序号不超过这个值的投递，回 204 |

`/relay/*` 都要中继密钥，缺了或不对回 401。

### 2. Node 跑法

`evdock relay serve [--db relay.db] [--host] [--port] --key-env <环境变量名>`

### 3. Worker 跑法

放在 `relay-worker/` 目录：Worker 入口、Durable Object 类、wrangler 配置。中继密钥用 `wrangler secret put` 设置。新增两个开发依赖：`wrangler`（MIT 或 Apache-2.0）和它带的 workerd，在 Windows 上一共约 175 MB，只用于开发和测试，不进运行时。

### 4. 守护进程改动

- `evdock relay use <中继地址> --key-env <环境变量名>`：把中继地址和环境变量名存进库里。`evdock relay clear`：取消中继。
- `subscribe`：配置了中继、又没给 `--callback-base` 时，回调基址就用中继地址。在 `events/subscribe` 之前登记路径，成功后确认，失败就删掉。
- 退订、收到 terminated、因永久错误停止续订：删除中继上的路径，尽力而为。
- `serve`：配置了中继就跑取回循环。取回的投递交给 M1 的 `handleDelivery`，收到时刻用中继记的那个。结果为 503（本地写失败）就停在这里，下一轮重取；其他结果都算处理完。一批处理完就确认到最后一条。网络出错就退避，从 5 秒开始，最长 60 秒。本地接收端照旧运行，直连模式的订阅不受影响。

### 5. 测试

- **`npm test`：**
  - 中继核心
  - Node 跑法
  - 守护进程配 Node 中继的端到端测试
- **`npm run test:worker`：** 用 `wrangler dev` 在本地起 Worker，不需要 Cloudflare 账号，跑同样的端到端场景。它依赖较重，所以和 `npm test` 分开。

### 6. 部署说明：`docs/relay.md`

写清楚三件事：
- 怎么部署到 workers.dev：注册账号、`wrangler login`、`wrangler deploy`、`wrangler secret put`。这些需要你自己的 Cloudflare 账号，由你来做。
- Node 跑法怎么配 TLS。
- 守护进程怎么连上中继。

## 验收

1. `npm test` 和 `npm run test:worker` 全部通过，贴出输出。
2. **Node 跑法实测：**
   - 订阅模拟服务端，TTL 3 分钟。
   - 强杀守护进程，离线 6 分钟。这超过了 5 分钟的时间戳窗口，也超过了服务端的重试窗口和 TTL。
   - 离线期间服务端一直产生事件：TTL 过期之前的经中继暂存，过期之后的靠重启时带游标重订补回。
   - 重新上线后，收件箱里的事件和服务端产生的完全一致，每个只出现一次，全部验签通过。
3. Worker 跑法（`wrangler dev` 本地）跑同样的场景。
4. **安全检查：**
   - 没带或带错中继密钥：401
   - 没登记的路径：404，也不会回显 challenge
   - 待确认路径收到事件：503
   - 超过 256 KiB：413，而且不读 body
   - 中继和守护进程的日志里没有密钥，也没有 body
5. 独立 subagent 的审查意见和处理结果。
6. `docs/decisions.md` 记下规范没写清、自己做了选择的地方。
