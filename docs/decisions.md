# 规范没写清、自己做了选择的地方

依据：`docs/spec/design-sketch-2026-10-06.md`（下称"草案"）和 `docs/spec/standard-webhooks-2026-10-06.md`（下称"SW"）。草案改了要回来对一遍。

## M1

### 开工前和你确认过的

| # | 选择 | 理由 |
| --- | --- | --- |
| 1 | 时间戳两个方向都查：和收到时刻相差超过 300 秒就拒，正好 300 秒收 | 草案只说"超过 5 分钟旧"（SHOULD）。SW 说"在容差内"，官方 `standardwebhooks` 库两个方向都拒。超前的时间戳同样能用来延长重放窗口。 |
| 2 | 去重键是（路径令牌, `webhook-id`），不是只有 `webhook-id` | 草案规定事件的 `webhook-id` 就是 `eventId`，且 SHOULD 用上游稳定 id。同一个上游事件命中两个订阅时 `webhook-id` 相同，只按 `webhook-id` 去重会把第二个订阅的事件当重复丢掉。 |
| 3 | 测试套件每项标 MUST / SHOULD / MAY / 未规定，只有 MUST 失败算不合格 | 草案对各项要求的强度不同，见下面"测试套件"一节。 |
| 4 | 套件不加查库接口；"重复不入库"由 `npm test` 查表证明 | 套件是黑盒，只看得到状态码。 |
| 5 | `engines.node` 写 `>=22.13` | `node:sqlite` 从 22.5 才有，22.13 起不用加 `--experimental-sqlite`。 |
| 6 | Standard Webhooks 规范也存快照 | 草案的签名细节引用它。 |

### 接收端状态码

草案只规定了 2xx（已接受）、413（MAY）、503 或 425（未确认，SHOULD），以及 410 表示"这条别重试"。其余是自己选的：

| 情况 | 状态码 | 说明 |
| --- | --- | --- |
| body 超过 256 KiB | 413 | 大于 262144 字节拒，正好 262144 收。超限后把剩下的读完丢掉再回 413，客户端能拿到状态码，而不是连接被重置。已知限制见文末。 |
| 路径没登记 | 404 | 按普通失败处理。草案里 410 的意思是"认出了这条投递，但不想被重试"，没登记的路径谈不上认出。 |
| 缺四个必需头之一 | 400 | |
| `webhook-timestamp` 不是整数秒（只允许 1 到 15 位数字） | 400 | |
| 验签失败 | 401 | |
| 时间戳超出 5 分钟 | 401 | 服务端每次重试都会重新生成时间戳，回可重试的状态码就行。 |
| body 不是合法 UTF-8 的 JSON 对象，或字段类型不对 | 400 | 必须先验签通过才会走到这一步。 |
| verification，签名和时间戳都通过 | 200，body `{"challenge":"<原样>"}` | 不管订阅确认没有都回。 |
| 路径已登记，订阅未确认 | 503 | 草案允许 503 或 425，按 DESIGN.md 选 503。 |
| `X-MCP-Subscription-Id` 和登记的 id 不一致 | 503 | 属于草案说的"这个 id 还没告诉接收方怎么路由"，草案要求回 503 或 425 这类可重试的码。最初写的 400，审查后改成 503。 |
| 重复的 `webhook-id` | 200 | 草案也允许回 410，选 200。 |
| 读库或写库失败 | 503 | 让服务端重试。 |
| 不是 POST | 405 | |
| 不是 `/hooks/<令牌>` 路径 | 404 | 请求目标按纯字符串匹配，不当 URL 解析。请求目标是外部可控的，不一定是合法 URL。带协议和主机的完整写法（`http://host/hooks/…`）先去掉协议和主机再匹配，HTTP/1.1 要求服务器接受这种写法。 |

### 请求头

- Node 把头的原始字节当 latin1 字符串交出来。发送方按 UTF-8 编码（签名串前缀规定是 UTF-8），所以先还原成原始字节，再按 UTF-8 解码，之后才去验签和入库。非 ASCII 的 `webhook-id` 因此能正确验签。
- `webhook-signature` 如果分成多行重复的头发送，按空格合并成一个列表。HTTP 默认用 ", " 合并，会让第一个签名后面多出逗号而验不过。

### 检查顺序

body 大小（读 body 时）→ 路径是否登记 → 四个必需头 → 时间戳格式 → 验签 → 时间戳窗口 → 解析 body → verification 回显 → 订阅是否确认 → 订阅 id 是否一致 → 写盘。

- 验签放在解析 body 之前：草案要求"验签之后才处理"。
- 时间戳窗口放在验签之后：两者都会拒，顺序只影响回哪个码，先认身份再查新鲜度。
- verification 放在"订阅是否确认"之前：服务端在激活投递之前发 verification，失败时让 `events/subscribe` 直接返回 -32015，所以握手一定发生在 subscribe 返回之前，那时订阅还没确认。

### 密钥按路径选

草案说 `X-MCP-Subscription-Id` 是为了"不解析 body 就能选对密钥"。但 verification 到达时接收方还不知道订阅 id（理由同上），所以 evdock 按路径令牌选密钥；`X-MCP-Subscription-Id` 只在订阅确认后用来核对。

### 消息分类

- 顶层有 `type` 字段就是控制包，不管值是什么；`type` 不是字符串回 400。
- 未知的 `type`：回 200，存进收件箱（kind 记为 `unknown_control`）。草案要求接收端把控制包转交给客户端，以后新增的控制包类型不该被拒掉。
- 事件只检查：`eventId` 是非空字符串，`name` 和 `timestamp` 是字符串，`data` 是对象，`cursor` 是字符串或 null 或不存在。`timestamp` 不检查 ISO 8601 格式，`_meta` 和其他字段照存不检查。
- 不检查事件里的 `eventId` 是否等于 `webhook-id`，去重只按 `webhook-id`。
- 不检查 `name` 是否和订阅的事件名一致：M1 不知道订阅的是哪个事件，等 M2。（M2 已补上，见 M2 一节。）
- `gap` 只检查 `cursor`；`terminated` 检查 `error.code` 是整数、`error.message` 是字符串。不合格回 400。

### 收件箱

- 三张表：`subscriptions`、`events`、`cursors`。`events` 除了事件，也存 gap、terminated 和未知类型的控制包（`kind` 列区分）。草案要求控制包"和事件走同一条通道"转交给客户端，M4 的输出端从这一张表读。
- verification 不入库，也不参与去重：服务端重发同一个 challenge 时要能再回显一次。
- body 存原始字节，不重新序列化。
- 开 WAL，`synchronous = FULL`。事务提交返回后才回 200。
- 游标：
  - 事件的 `cursor` 不为 null 才保存，覆盖旧值。草案规定 null 不能持久化；而且同一事件类型要么一直有游标，要么一直是 null。
  - 按到达顺序保存。草案说最近收到的游标总是安全的（它是水位线，不是这条事件自己的位置）。
  - 重复投递不动游标。
  - gap：`cursor` 不为 null 就覆盖保存，并且 `possible_gap = 1`；`cursor` 为 null 只做标记。`possible_gap` 由以后的消费方清除（M2/M4）。
- terminated（M2 起改为把订阅标记为 terminated，不再删行，见 M2 一节）：删掉订阅行，消息本身留在 `events` 表，作为给输出端的通知。之后这条路径的投递回 404。游标行保留：草案要求重新订阅时带上最后保存的游标（比如因为 schema 变更被 terminated 后重新订阅），删掉就找不回来了。要不要用它由 M2 决定。最初写的是连游标一起删，审查后改了。

### 签名

- 签名串：`webhook-id + "." + webhook-timestamp + "."` 按 UTF-8 编码，后面直接接原始 body 字节。时间戳用头里的原字符串，不重新格式化。
- `webhook-signature` 按单个空格切分，空项跳过；只认 `v1,` 开头的项，`v1a,` 等其他前缀忽略，哪怕值碰巧对得上。
- 比较的是 base64 字符串：长度不同直接判不等（SHA-256 的签名长度是公开的 44 字符），长度相同用 `timingSafeEqual`。
- 密钥：`whsec_` 后面必须是标准 base64（长度是 4 的倍数），解码后 24 到 64 字节。

和官方 `standardwebhooks` 库（1.1.1）的两处差别，测试里避开了：
- 库用 `parseInt` 解析时间戳后再格式化回字符串去签名，所以 `0017…` 这种头在库里和在这里结果不同。这里按草案签头里的原字符串。
- 库把 Buffer 形式的 body 先按 UTF-8 解码成字符串再签，非 UTF-8 字节会变。这里签原始字节。

### 日志

每个请求一行：状态码、结果、路径令牌前 6 位、`webhook-id`（不可见字符换成 `?`，截到 80 字符）。不记 body，不记密钥，不记完整令牌。不检查 `Content-Type`。

### 本地运行

- `evdock serve` 默认只监听 `127.0.0.1:8787`，明文 http。
- `evdock register` 是 M2 之前手工登记路径的临时命令，会把 `whsec_` 密钥打到 stdout，因为扮演服务端的测试套件需要它，相当于正式流程里 `events/subscribe` 把密钥交给服务端。只用于本地测试，M2 用订阅管理替换。

### 测试套件

套件扮演服务端，对一个接收地址发 15 个请求场景，只依赖 Node 自带模块，不引用 evdock 自己的代码。输出是英文，因为 M4 要提交到工作组仓库。

| 场景 | 等级 | 期望 | 等级依据 |
| --- | --- | --- | --- |
| valid-event | MUST | 2xx | 基线；这项不过，其余结果没有意义 |
| bad-signature | MUST | 非 2xx | 接收方 MUST 先验签再处理 |
| stale-timestamp | SHOULD | 非 2xx | 草案：SHOULD 拒绝超过 5 分钟的。用 10 分钟前，避开边界和时钟误差 |
| replay | SHOULD | 2xx，然后 2xx 或 410 | 去重是 SHOULD；黑盒只能看状态码 |
| retry | SHOULD | 2xx，然后 2xx 或 410 | 同上 |
| rotation | MUST | 两次都 2xx | 草案："任一签名通过即接受"。新旧顺序各测一次 |
| raw-body | MUST | 2xx | 接收方 MUST 对原始 body 算 HMAC |
| verification | MUST（有条件） | 2xx，且 body 的 challenge 一致 | 草案给了四种证明接收意愿的方式，握手只是其一。默认计入；接收方用白名单、带外登记或 well-known 文档时加 `--no-handshake`，这项就只记录不计入。最初是无条件计入，审查发现会把合规的接收方判成不合格，于是加了这个开关 |

## M2

依据：`docs/spec/sep-3415-2026-10-06.md`（下称 SEP）、`docs/spec/mcp-2026-07-28/`（下称基础规范）、OpenAI 的 MCP Events 文档（下称 OpenAI 文档，本地快照）。开工前和你确认过的几条见 `docs/M2-TASK.md`。

### 客户端

| 选择 | 理由 |
| --- | --- |
| 只说 2026-07-28，不回退到带 `initialize` 的旧版 | SEP 只定义在 2026-07-28 上，OpenAI 文档也要求这个版本。服务端不支持就报错并列出它支持的版本。 |
| `server/discover` 每个守护进程对每个服务端只调一次；命令行每次都调 | SEP 要求没声明扩展的服务端不能收到 `events/*`。discover 结果本可缓存（`ttlMs`），守护进程活着期间不再重查，够用。 |
| 能力在 `extensions["io.modelcontextprotocol/events"]` 或顶层 `events` 都算 | SEP 用前者；草案和 OpenAI 文档用后者，SEP 自己也说"至少有一个已部署的客户端读顶层"。 |
| 错误码两套编号都认 | 草案 -32011…-32015，SEP -32023…-32027（暂定），OpenAI 文档用 -32015。 |
| `resultType` 缺失当 `complete`，其他值报错 | 基础规范的要求；OpenAI 文档的示例结果没有这个字段。 |
| 响应在拿到 JSON-RPC 结果前断了（正常结束或连接被重置都算），换新 id 重发一次；超时不重发 | 基础规范 2026-07-28 的变更记录要求重发（`docs/spec/mcp-2026-07-28/changelog.mdx` 第 28 行）；`events/*` 都是幂等的。只重发一次，再断就算这次失败，交给续订的退避。 |
| 对 MCP 端点的请求不跟随重定向 | 带着 bearer 令牌跳到别处不安全；规范没要求跟随。 |
| 请求超时 30 秒 | 规范没定。 |

### 订阅和续订

| 选择 | 理由 |
| --- | --- |
| 不发 `ttlMs`，用服务端默认 | 少一个配置项；SEP 说省略即服务端默认。因为从不请求无期限，正常不会拿到 `refreshBefore: null`；万一拿到，每小时续一次。 |
| 不发 `maxAgeMs` | 任务书已定：M2 不做，重放不设上限。 |
| 授予时长过了 2/3 就续订，两次续订至少隔 1 秒 | 规范只说"在 refreshBefore 之前"。2/3 留出了失败重试的余量；1 秒下限防止服务端给出过短或已过期的时间时狂刷。 |
| 续订失败按 1、2、4…秒退避，最多 60 秒，过了 `refreshBefore` 也继续 | 过期后再调 `events/subscribe` 会带着游标新建订阅（SEP），所以一直试下去是对的。 |
| 停止续订的错误：Forbidden、NotFound、Unsupported、InvalidParams、MethodNotFound；其余都重试 | 前几种重试也不会变；CallbackEndpointError（接收端暂时不通）、ResourceExhausted、网络和 5xx 都可能自己恢复。因 schema 变更被停的不自动重订（任务书不做）。 |
| 守护进程启动时，有游标的订阅一律"先退订、再带游标订阅"，失败了就按退避重试，直到成功或订阅停止为止，中途不会退回普通续订；游标为 null 的只做普通续订 | 规范缺口，见 `docs/M2-TASK.md`。不按停机时长判断，规则最简单，代价是会收到一些重复（按 webhook-id 去重）。游标为 null 的类型本来就补不回停机期间的事件，退订再订只会多一个空窗。最初只试一次，失败后就退回普通续订，缺口又会打开，审查后改了。 |
| `subscribe` 失败就删掉刚登记的路径 | 没成功的订阅不该留下能收投递的路径。如果服务端其实建成了但响应丢了，它的投递会得到 404，到期自然清掉。 |
| 回调地址存在每个订阅上，默认基址 `http://127.0.0.1:8787` | 回调 URL 是订阅键的一部分，续订必须一字不差。M2 没有中继，只能填本机或隧道地址。 |
| arguments 按 JSON 文本存，续订时原样解析再发 | 服务端按规范化 JSON 比较，键序不影响，但原样重发最稳妥。 |
| 退订时服务端回 NotFound 当成功；本地状态改成"已退订"，路径从此回 404 | OpenAI 文档要求幂等，SEP 回 NotFound，两种都接受。 |
| terminated 只改状态，不删行；续订响应若晚于 terminated 到达，不会把订阅重新激活 | 已确认的改动。避免续订和 terminated 赛跑时把已结束的订阅救活。 |
| `deliveryStatus.active === false` 在日志里告警；`throttled` 记一条 | DESIGN.md 要求告警；规范说这两个字段只是提示。 |

### 存储和进程

- `servers` 表只存令牌所在的环境变量名，令牌本身不落盘、不打日志。
- 命令行和 `serve` 是两个进程，共用一个 SQLite 文件：开 `busy_timeout = 5000`。
- 不做数据库迁移：M2 之前没有实际部署。打开 M1 格式的文件时直接报错，让人删掉重建，不会读错。
- 日志里订阅用服务端给的 id 表示，没有 id 时用路径令牌前 6 位；不记密钥、不记令牌。

### 测试用服务端

- 两个测试服务端都有 `allowInsecureCallbacks` 开关，默认关闭，打开后接受 http 和本机回调地址。规范要求回调必须 https 且拦截内网地址，这是为了在没有中继的 M2 里本地测试。

#### 模拟服务端（`src/conformance/mock-server.ts`，按 SEP-3415）

- 事件自己载荷里的游标可以覆盖到它自己：SEP 535 行说，前面的事件都确认或放弃之后，事件 N 就可以带 cursor_N；接收方只有存下 N 才会存这个游标。订阅和续订响应里的游标仍然严格不越过任何未确认的事件。
- TTL：取客户端建议值和默认值中较小的那个；`ttlMs: null` 也授予有限期限，因为这个模拟服务端只存在内存里（SEP 允许）。
- 握手失败的原因：对方回 4xx/5xx 记为 `http_4xx`/`http_5xx`；回了 2xx 但没有正确回显记为 `challenge_failed`。SEP 609 和 626 行在这点上说法不一。3xx 没有对应的类别，算作 `http_4xx`。
- 收到它不认识的游标（比如别的实例发的，相当于服务端重启过）：从当前位置开始投递，并返回 `truncated: true`。
- 握手结果在实例存活期间一直缓存；失败的不缓存。
- 方法级错误用 HTTP 200 返回；头和 `_meta` 出错用 400；未知方法用 404 加 -32601。没带令牌回 HTTP 401，不是 JSON-RPC 的 Forbidden。
- 没做：轮换期间双签名（SHOULD），以及失败后把投递置为暂停（`active: false`）。

#### 按 OpenAI 文档写的示例服务端（`test/fixtures/openai-server.ts`）

- 文档和规范冲突时照文档，代码里都标了"Guide over spec"：能力声明在顶层 `events`；`events/*` 的结果不带 `resultType`；用 -32015；退订幂等，返回 `{}`；不发 gap 和 terminated；游标恒为 null；订阅存在 JSON 文件里，重启后还在。
- 文档只给了 -32015 一个错误码，其余错误码按它引用的草案取（-32011、-32014）。
- 签名照文档里的 Node 示例，用 `standardwebhooks` 库，所以轮换期间不双签名。
- Node 自带的 `fetch` 做不到"连接时先检查地址再连上这个地址"，所以文档里的 `webhookFetch` 用 `node:http(s)` 实现，对 IP 字面量单独检查，不跟随重定向。

### 审查后补充的选择

| 选择 | 理由 |
| --- | --- |
| 旧编号 -32011…-32015 要有佐证才算数：message 对得上名字，或 `data` 带着该错误特有的字段（kind、limit、feature、reason）；对不上就当未知错误，重试 | 基础规范 2026-07-28 说接收方 MUST NOT 假定 -32000…-32019 有特定含义（`basic-index.mdx` 117–121 行），别的实现可能把它们用在别处。新编号 -32023…-32027 直接认。 |
| `refreshBefore` 缺失或不是时间戳就当错误，只有显式的 `null` 才是无期限 | SEP 说它总会出现。猜一个期限会掩盖服务端的错误。 |
| 续订响应 `truncated: true` 但游标为 null：不标记"可能漏了" | SEP 709 行：没有重放的类型不该置 `truncated`，客户端 SHOULD 忽略。 |
| 事件的 `name` 和订阅的事件名不一致：回 400，不入库 | OpenAI 文档要求一致。收下错类型的事件，到 M4 可能触发错误的动作。没有事件名的路径（测试里手工登记的）不检查。 |
| 续订调用期间订阅已经结束（本地退订，或收到 terminated），而这次调用可能在服务端重新建了订阅：再发一次 `events/unsubscribe` | 否则服务端会一直往一个回 404 的路径投递，直到过期。 |
| "已停止"和 terminated 都只能从"活动"状态转过去 | 避免盖掉已经结束的状态和它的原因。 |
| 服务端给的文字（错误消息、事件描述、`lastError`）打印或入库前，把控制字符换成 `?` 并截断 | 和 M1 处理 `webhook-id` 的做法一致，防止往终端里注入控制序列。 |
| JSON 响应的 id 必须和请求的一致；`Content-Type` 不区分大小写；SSE 里不带冒号的 `data` 行按空值处理 | 都是 SSE 和 JSON-RPC 本身的规定。 |
| `serve` 每秒检查一次哪些订阅该续了 | 真实的 TTL 以分钟计，1 秒的粒度没有影响。测试里 TTL 只有 3 秒，续订可能落在快过期的时候，所以测试把检查间隔调到 50 毫秒。 |

## M3

依据：`docs/spec/sep-3415-2026-10-06.md`（下称 SEP）和 `docs/spec/cloudflare-2026-10-06/`。开工前和你确认过的选择见 `docs/M3-TASK.md` 的"设计决定"：不发布 well-known 文件、短轮询、路径三种状态、按中继收到的时刻查时间戳、存到确认取回才删、一份核心两种跑法。

### 中继

| 选择 | 理由 |
| --- | --- |
| 握手包只要路径已登记就回显 challenge，不验签 | 中继没有密钥（DESIGN 已定）。路径是守护进程登记的随机令牌，登记本身就是同意接收，握手要证明的正是这件事。 |
| 只解析 4 KiB 以内的 body 去识别握手包，更大的一律当事件原样存 | 握手包很小；不去解析大 body，省 Worker 的 CPU（免费层每次 10 ms）。 |
| 必需头缺一个就回 400 | SEP 655 行允许中间设备这样预过滤；省掉存一条注定验不过的投递。 |
| 先看 `Content-Length`，超 256 KiB 直接回 413；没有长度的，读到超限就停止读取 | 不为注定要拒的 body 花存储和 CPU。 |
| Node 跑法回了 413（或 404）之后，先把还没读的 body 最多再读 1 MiB 丢掉，再写响应；剩下的超过 1 MiB 就断开连接 | 不读完就关连接，发送方只看到连接被重置，会当网络错误一直重试；而 413 按规范是"不必再试"。试过先写响应再丢弃剩余部分：远没到上限的 body，发送方也看到连接重置。1 MiB 是"还没读的部分"：按 `Content-Length` 拒绝时一个字节都没读，所以总长超过约 1 MiB 的 body 会被断开、拿不到 413，但这种 body 已经远超规范建议的 256 KiB，断开即可。这和任务书第 8 条的"回 413 并断开连接"不完全一样，审查时指出过。M1 的本地接收端改成同样的规则。 |
| 路径令牌 16 到 128 位，字符限 `A-Z a-z 0-9 _ -` | 守护进程生成的是 32 位，留了余量；拒掉明显不是令牌的东西。 |
| 中继密钥：比较两边的 SHA-256 摘要 | 比较时间和密钥在哪一位不同、长度多少都无关。两种跑法都只用 Web Crypto。 |
| 总量上限 1 万条或 200 MB（body 加上请求头一起算），满了回 503；计数放在一行"合计"里，不用每次 `count(*)` | 每次投递只读一行，不随积压变多而变贵，省免费层的 rows read。请求头也算进去：Cloudflare 允许单个请求带最多 128 KB 的请求头。 |
| 一次取回最多 20 条，body 合计不超过 512 KiB（至少给 1 条），并告诉守护进程后面还有没有 | 控制单次响应的大小。最初的理由是"免得超出 Worker 每次 10 ms 的 CPU"，审查指出不成立：10 ms 是前面 Worker 的限制，它只转发；Durable Object 每个请求默认 30 秒 CPU（`durable-objects_platform_limits.md` 第 31 行；但同页第 17 行又说按 Workers 计划的限额，有歧义，所以编码照样做了优化）。base64 编码优先用运行时自带的 `toBase64`，没有的话按 32 KB 一段用 `apply` 拼接（审查实测比展开运算符快约 6 倍）。 |
| 确认按序号累积（`upTo`），删掉序号不超过它的全部 | 守护进程按顺序处理，一个数字就够了。 |
| 删除路径时，连带删掉它没取走的投递 | 路径删了，守护进程那边的订阅也已结束，这些投递取回来也只会是 404。 |
| 日志：状态码、结果、令牌前 6 位、`webhook-id`；不记 body、密钥、完整令牌 | 和本地接收端一致。 |

### 守护进程

| 选择 | 理由 |
| --- | --- |
| 配了中继、`subscribe` 又没给 `--callback-base` 时，回调走中继 | 中继就是为没有公网地址的情况准备的；显式给了地址就尊重它。 |
| 中继上的路径：订阅前登记为"待确认"，拿到授权后本地先改成活动、再到中继上确认；`subscribe` 失败就删掉 | 中继存下的投递，订阅一定已经在本地生效，取回时不会撞上"未确认"。 |
| 每次续订成功后、以及守护进程启动时，都再确认一遍路径（幂等） | 万一某次确认没发成功，或者中继丢了数据，会自己恢复。代价是每次续订多一个请求。 |
| 退订、因永久错误停止、收到 terminated、续订时发现订阅已结束：都把路径从中继删掉，失败只记日志 | 这些订阅不会再有投递；路径留着也只是让中继多存几条取回后 404 的东西。 |
| 取回的投递交给 `handleDelivery`，收到时刻用中继记的那个 | 和直连时走完全相同的检查。 |
| 只有本地写库失败（`store-failed`、`inbox-unavailable`）才不确认、下一轮重取；其他结果都确认，包括 401、404、400 和意外抛出的异常 | 这些结果重取一百次也一样。卡住一条会让后面全部堵住。 |
| 有更多就立刻再取；出错按 5、10、20、40、60 秒退避 | 积压尽快清空；中继暂时不可用时不狂刷。 |
| 中继模式下本地接收端照常运行 | 直连模式的旧订阅不受影响。 |
| `evdock relay clear` 不迁移已有订阅 | 回调地址是订阅键的一部分，换地址就是另一个订阅；要换就退订再订。 |

### Worker 跑法

| 选择 | 理由 |
| --- | --- |
| 一个 Worker 加一个 Durable Object（`idFromName('relay')`），Worker 等它的响应回来才回 | Durable Object 的 output gate 保证响应在写盘之后才发出（Cloudflare 文档 rules-of-durable-objects），所以 2xx 一定在落盘之后。 |
| BLOB 直接绑 `Uint8Array`，读回来的 `ArrayBuffer` 转成 `Uint8Array` | 本地 workerd 实测接受 `Uint8Array`；转换之后核心看到的类型和 `node:sqlite` 一样。 |
| 用 `migrations` + `new_sqlite_classes` 声明类，不用新的 `exports` 写法 | 两种都能用，但不能混用，一旦用 `exports` 部署过就回不去了；`migrations` 是文档里写全了的那种。 |
| `compatibility_date` 设 2026-10-01 | 固定版本的 wrangler 自带的 workerd 最新只支持到这一天。 |
| `send_metrics: false` | 不把这个项目的 wrangler 使用数据发给 Cloudflare。 |
| 本地测试把密钥放在 wrangler 进程的环境变量里，不用 `--var` | `--var` 的值会被 wrangler 打印在启动时的绑定表里。 |
| 核心里 `TextDecoder` 的选项写全 `{ fatal: true, ignoreBOM: false }` | Workers 的类型定义要求两个都给；行为不变。这样就不用修补生成的类型文件。 |

### 已知限制

- `wrangler dev` 本地代理在中继不读 body 就回 413 时，会把这条连接断掉，下一个 POST 可能拿到 500。测试里多发两个 GET 绕过。部署到 Cloudflare 之后是否也这样，本地验证不了。
- Cloudflare 自己的日志（`wrangler tail`、Workers Logs）会记录完整的请求地址，包括路径令牌。这些日志在用户自己的账号里；拿到令牌只能往这条路径塞注定验签失败的投递。已写进 `docs/relay.md`。
- 中继如果长时间不可用（比如用完了当天的免费额度），服务端的重试会用尽，事件被放弃，也就是那个规范缺口。守护进程只在启动时做"先退订、再带游标订阅"，所以中继恢复后要重启一次 `evdock serve` 才能补回。可以让守护进程在中继恢复时自动重订，但这超出 M3 的范围，先记在这里。

### 审查后补充的选择（M3）

| 选择 | 理由 |
| --- | --- |
| 请求头的值按发送方的本意存：Node 跑法把 Node 交出来的 latin1 字符串还原成原始字节，再按 UTF-8 解码（和本地接收端一样）；Worker 跑法 workerd 本来就是这样 | 审查发现，非 ASCII 的 `webhook-id` 在 Node 中继里会被存成乱码：中继回 200，守护进程验签失败，事件就悄悄丢了。这些值放不进 `Headers` 对象（它只接受字节串），所以核心改成接受一个"读请求头"的函数。 |
| 分成多行发送的 `webhook-signature`，在中继存储前合并成用空格分隔的列表 | HTTP 会用 ", " 把重复的头拼起来，于是除了最后一个，每个签名后面都多了个逗号，验不过。签名项的形式是 `v<n>,<base64>`，base64 里没有逗号，所以 ", v1," 只可能是两项的分界。本地接收端在 M1 就已经这样处理。 |
| 只要还有订阅（活动或待确认）的回调地址在当前中继上，`relay clear` 和换地址的 `relay use` 就拒绝，并列出这些订阅 | 否则服务端继续往旧中继投递、拿到 2xx，守护进程却不再去取，事件悄悄丢失。同一个地址只是换密钥变量名，不受限制。 |
| `relay use` 给远程主机配 http 地址时打警告 | 中继密钥和事件会明文传输。本机地址不警告，方便本地测试。 |
| `subscribe` 之后到中继上确认路径，失败就重试 3 次（间隔 1、2 秒），还不行就打警告 | 没确认之前中继对事件回 503，服务端的重试在一点点耗尽；而下一次自动确认要等第一次续订。 |
| `evdock events` 不加载中继，不要求中继密钥 | 列事件和中继无关。 |
| Worker 只把 `/hooks/` 和 `/relay/` 交给 Durable Object，其他路径直接 404 | 不为杂乱请求花 Durable Object 的请求额度。 |
| wrangler 配置里不声明 `secrets.required` | 声明了之后，首次 `wrangler deploy` 会因为 secret 还没设而拒绝执行，而 Worker 不存在时 secret 又设不了。现在先部署，再 `wrangler secret put`；设好之前中继回 500。本地测试通过 `CLOUDFLARE_INCLUDE_PROCESS_ENV` 让 `wrangler dev` 从进程环境变量读密钥。 |
| Worker 的端到端测试共用一个 Worker 中继 | 每个场景各起停一次 wrangler 很慢，而且在 Windows 上刚被杀掉的 workerd 会短暂占着端口和文件。各场景用的都是新路径，互不影响。 |

## M4

开工前和你确认过的见 `docs/M4-TASK.md` 的"设计决定"：只做动作执行器、本地 MCP 服务暂不做、命令不经过 shell、事件只走 stdin、默认 10 秒合并窗口和每小时 6 次上限、失败按 1/5/15 分钟重试后跳过、"至少一次"、30 分钟超时、演示不需要账号、README 用英文。

### 动作执行器

| 选择 | 理由 |
| --- | --- |
| 每个订阅最多一条动作；`action set` 重复执行就是替换，处理进度保留 | 简单；替换命令（比如修好了脚本）不应该让已经处理过的消息再跑一遍。 |
| 新配的动作从"当前最后一条消息之后"开始 | 配动作是"以后有事就叫我"，不是"把历史全部重放一遍"。 |
| 一批最多 100 条消息，剩下的进下一批 | 守护进程离线很久后积压可能很多；不能把几百 MB 一次塞进 stdin。 |
| 合并窗口从这一批里最早那条消息的收到时刻算起 | 守护进程离线回来时，积压的消息早已过了窗口，立刻就跑，不会再白等。 |
| 每小时上限按"命令启动次数"算，失败的那次也算；记录存在库里，恰好一小时前的那次不再计入 | 上限是为了保护 agent 和你的额度：失败重试也会消耗它们。存进库里，重启守护进程就绕不过去。 |
| 第一次失败后再试三次（等 1、5、15 分钟），第四次还失败就跳过这批，打 `WARNING` | 任务书写的是"按 1、5、15 分钟重试，三次都失败就跳过"。跳过是为了不让一批坏数据卡住后面所有消息。 |
| 超时只结束直接启动的那个进程，它再启动的子进程不一定会一起结束 | Node 的 `kill` 只作用于直接子进程。要结束整棵进程树得分平台处理，v0 先不做；30 分钟的超时本来就很少触发。 |
| `serve` 停止时结束正在跑的命令，这批不算完成，下次启动重跑 | 和"至少一次"一致；停止 `serve` 不该被一个跑得很久的 agent 拖住。 |
| 命令的 stdout/stderr 直接显示在 `serve` 的终端里 | 最简单，方便看 agent 在做什么。evdock 自己的日志行仍然不含事件内容。 |
| stdin 里 `messages[].body` 是解析好的 JSON 对象 | 入库前已经验过签、解析过；交给命令的是"可以直接用的数据"，原始字节留在库里。 |
| `--` 之后的全部参数原样作为命令，`--` 之前才按选项解析 | 命令自己的参数可能也长得像选项（比如 `--db`），不能被 evdock 吃掉。 |

### 演示和文档

| 选择 | 理由 |
| --- | --- |
| 演示服务端复用模拟服务端，固定令牌 `demo-token`，端口 8790，每 15 秒编一条事件；打开 `allowInsecureCallbacks` | 不需要任何账号，本机直连就能跑；15 秒加 10 秒窗口，第一次唤起在 25 秒内。 |
| README 的 Windows 例子：通过 `cmd.exe /d /s /c` 运行 `.cmd`，并说明固定提示词里不要有 `" & | < > ^ %` | 实测过，带空格的提示词会作为一个完整参数传到 `.cmd`。cmd 只解析这条固定命令行，事件始终只在 stdin。 |
| README 写明 PowerShell 5.1 里 JSON 参数要写成 `'{\"k\":\"v\"}'` | 实测 PowerShell 5.1 传给原生命令时会吞掉双引号。 |
