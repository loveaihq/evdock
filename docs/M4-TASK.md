# M4：动作执行器和发布

2026-10-06 确认。发布的两步做之前另外确认。

收到事件时唤起本地 agent，写好 README，公开项目并报给工作组。验收标准是：没接触过项目的人照着 README 能跑通演示。

## 设计决定

### 1. 输出只做动作执行器，本地 MCP 服务不做（和 DESIGN.md 不同）

DESIGN.md 的"输出"有两条路：一个本地 MCP 服务，把事件以 poll 或 push 的方式再提供给支持 Events 的 agent；一个动作执行器，事件到了就跑一条命令。

M4 只做动作执行器。理由：
- 目前查到的资料里，没有本地 agent 能消费 MCP Events 的 poll 或 push。已知部署了的客户端只有 ChatGPT，而它走的是 webhook。
- 动作执行器不依赖 agent 支持 Events，任何命令行 agent 都能被它唤起，比如 Claude Code 的 `claude -p`。

本地 MCP 服务等真有 agent 能用了再做。DESIGN.md 的组件职责跟着改。

### 2. 动作执行器

- **怎么配：** 每个订阅最多配一条动作，配置存在库里。
  ```
  evdock action set <订阅> [--max-per-hour N] [--window 秒] -- <命令> [参数...]
  ```
  命令和参数原样存成数组，执行时不经过 shell。
- **事件怎么传进去：** 只通过 stdin，格式是一段 JSON：`{subscription: {...}, messages: [...]}`。命令行里从来不出现事件内容（DESIGN 已定），所以事件内容不可能变成命令注入。
- **合并窗口：** 第一条新消息到达后，等 `--window` 秒（默认 10 秒），把这段时间内到的消息合成一批，只唤起一次。
- **频率上限：** 每小时最多唤起 `--max-per-hour` 次（默认 6）。超了不丢消息，攒着等下一个允许的时刻，到时合并成一批。
- **成功和失败：** 命令退出码为 0 才算这批处理完，进度存进库里。失败后按 1、5、15 分钟重试，三次都失败就跳过这批，并打一条警告，免得一批坏数据卡死后面所有消息。
- **重启时：** 守护进程在命令运行中途崩溃，重启后会把这批再跑一次。也就是"至少一次"，agent 那边要能容忍重复。消息里带着 `eventId`，可以用来去重。
- **超时：** 单次运行最多 30 分钟，超时就结束进程，按失败处理。
- **哪些消息会交给命令：** 事件、gap（可能漏了事件）、terminated（订阅已结束）、未知类型的控制包都会交过去，每条带上 `kind`。DESIGN 要求 terminated 要通知到输出端，就是通过这里。
- **日志：** 只记哪条动作在什么时候启动、处理了几条、退出码、用了多久。不记事件内容。命令自己的输出直接显示在 `serve` 的终端里。
- **Windows 的 `.cmd`：** Node 不经过 shell 就跑不了 `.cmd` 文件，而 npm 装的命令（包括 `claude`）在 Windows 上都是 `.cmd`。README 里写明这种情况的用法：`cmd.exe /d /s /c claude -p "..."`。命令模板是固定写死的，所以经过 cmd 也没有注入风险。

### 3. 演示：任何人都能跑，不需要账号

- **随项目附带的演示：** `examples/` 下放三样东西：
  - 一个演示服务端：模拟服务端加一个"每隔几秒产生一条事件"的开关；
  - 一个替身 agent：从 stdin 读事件，打印"agent 被唤起，收到某事件"；
  - README 里的分步命令。
  
  整个演示用直连模式，不需要中继，也不需要任何账号。
- **真 agent 的写法：** README 另给一段，把动作换成 Claude Code（`claude -p`）或其他命令行 agent。
- **真跑一次 Claude Code（可选）：** 这台机器上没装 Claude Code 命令行（`claude`）。要真跑"事件唤起 agent"，需要你先装好并登录，这得你自己来。装好以后，我用一次很短的 `claude -p` 调用跑一遍，会用掉你一点额度。不装也不影响 M4 完成。

### 4. README

用英文写，读者是工作组和其他想用的人。内容包括：
- evdock 是什么、解决什么问题
- 架构图
- 安装
- 五分钟演示
- 接真实服务端：中继部署见 `docs/relay.md`
- 动作执行器怎么配
- 安全说明：事件内容不可信；事件不等于授权
- 一致性测试套件怎么用：测接收端用 `evdock-conformance`；测客户端用模拟服务端
- 已知限制，包括上报给工作组的那个规范缺口
- 许可证，以及规范快照的出处

`docs/` 里的任务书和 decisions 保持中文。

### 5. 发布

都是对外操作，每一步发之前都先给你看：
1. **把仓库公开到你的 GitHub。** 建议 `loveaihq/evdock`。
   - **前提一：** 先把 M1 那 4 个提交上的工作邮箱改掉（原地址不写进文档）。改写历史这步我这边被权限拦了，需要你自己跑之前给过的那条 `git rebase` 命令。不改的话，邮箱会跟着历史一起公开。
   - **前提二：** OpenAI 文档的快照已经排除在仓库之外，其他快照的许可都允许公开。
2. **在工作组仓库发一份 field report。** 格式照已有的那几份：
   - 介绍 evdock：接收端、中继、客户端这几块；
   - 和两种服务端写法互通的结果；
   - 接收端一致性测试套件；
   - 表示愿意把接收端和客户端的测试移植进官方一致性测试仓库（服务端那部分在 #521 进行中）。
3. **不做：**
   - 发布到 npm（没人要求）；
   - 直接给官方一致性测试仓库提 PR：那要按他们的框架重写，还要等 SEP 编号这些问题定下来，适合等工作组回应后单独做。

## 交付

1. `src/actions.ts` 和 `serve` 里的调度循环，收件箱里加 `actions` 表，命令行加 `action set` / `action clear` / `actions`。
2. `examples/` 里的演示服务端和替身 agent。
3. `README.md`，以及 `docs/relay.md` 的更新。
4. DESIGN.md 里关于本地 MCP 服务的修改。
5. 测试：
   - 窗口合并
   - 频率上限
   - 失败重试和跳过
   - 超时
   - 重启后重跑
   - 不经过 shell，事件内容不进命令行：用含 shell 元字符的事件验证
   - stdin 的格式
   - 控制包也会交过去

## 验收

1. `npm test`、`npm run test:worker`、`npm run typecheck:worker` 全部通过，贴出输出。
2. **README 实测：** 起一个完全没有上下文的 subagent，在一个干净的克隆里只看 README 跑演示，报告每一步的结果和卡住的地方。卡住的地方改 README，直到它一次跑通。
3. **Claude Code 实测（你装好命令行的话）：** 一个事件唤起本机的 Claude Code，贴出它的输出。
4. 独立 subagent 的审查意见和处理结果。
5. `docs/decisions.md` 记下规范没写清、自己做了选择的地方。
6. 发布的两步，你看过之后再做。
